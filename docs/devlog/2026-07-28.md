# 트러블슈팅

## 1. 이미지 파일이 요청 DTO에 바인딩되지 않는 문제

### 증상

작성 화면에서 여러 이미지를 선택해도 서버의 `GrowthRecordRequest`에서 파일 목록을 정상적으로 받지 못했다.

### 원인

JSP 파일 입력의 이름은 `imageFiles`였지만 DTO 필드명은 `imageFile`이었다. 또한 파일 전송 폼에 `multipart/form-data` 설정이 필요했다.

### 해결

- DTO 필드명을 `imageFiles`로 통일
- 작성 및 수정 폼에 `enctype="multipart/form-data"` 추가
- 서비스에서 `request.getImageFiles()`를 사용하도록 변경

```java
private List<MultipartFile> imageFiles;
```

```html
<form method="post" enctype="multipart/form-data">
    <input type="file" name="imageFiles" multiple>
</form>
```

### 결과

여러 이미지가 `List<MultipartFile>`로 정상 바인딩되어 S3 업로드 로직에 전달되도록 수정했다.

## 2. AWS 자격 증명을 찾지 못하는 문제

### 증상

환경에 따라 애플리케이션 시작 또는 S3 요청 과정에서 AWS 자격 증명을 찾지 못했다.

```text
Unable to load credentials from any of the providers in the chain
```

### 원인

- 특정 환경변수 이름에만 의존
- 설정 파일에 키가 있어도 `DefaultCredentialsProvider`만 사용
- 로컬, CI, AWS 실행 환경의 자격 증명 제공 방식이 서로 다름

### 해결

프로젝트 환경변수와 AWS 표준 환경변수를 모두 지원하도록 구성했다.

```yaml
cloud:
  aws:
    credentials:
      access-key: ${AWS_ACCESS_KEY:${AWS_ACCESS_KEY_ID:}}
      secret-key: ${AWS_SECRET_KEY:${AWS_SECRET_ACCESS_KEY:}}
    region:
      static: ${AWS_REGION:ap-northeast-2}
```

키가 명시된 경우 `StaticCredentialsProvider`, 키가 없는 경우 AWS 기본 자격 증명 체인을 사용하도록 분기했다. 두 키 중 하나만 설정된 경우에는 애플리케이션 시작 단계에서 오류를 발생시키도록 검증했다.

### 결과

로컬 환경변수, AWS 표준 환경변수, IAM Role 등 다양한 실행 환경에서 동일한 설정 구조를 사용할 수 있게 되었다.

## 3. S3 오류의 실제 원인을 구분하기 어려운 문제

### 증상

S3 업로드, 삭제, 접근 URL 생성 실패가 모두 비슷한 예외로 처리되어 권한, 인증, 네트워크 중 어느 부분이 원인인지 확인하기 어려웠다.

### 원인

AWS 응답 오류와 SDK 클라이언트 오류를 하나의 일반적인 예외로 처리했다.

### 해결

- `S3Exception`: 권한, 버킷, 요청 오류 등 AWS 응답 문제로 처리
- `SdkClientException`: 자격 증명 탐색 또는 네트워크 문제로 처리
- AWS 응답 메시지를 포함하는 공통 오류 메시지 생성 메서드 추가

### 결과

S3 장애가 발생했을 때 오류 유형과 원인을 이전보다 빠르게 파악할 수 있게 되었다.

## 4. 지원하지 않는 이미지 형식이 업로드될 수 있는 문제

### 원인

기존 서버 검증은 MIME 타입이 `image/`로 시작하는지만 확인해 서비스에서 지원하지 않는 형식도 통과할 수 있었다.

### 해결

서버에 허용 MIME 타입 화이트리스트를 적용했다.

```java
private static final Set<String> ALLOWED_IMAGE_TYPES = Set.of(
    "image/jpeg",
    "image/png",
    "image/webp"
);
```

브라우저의 `accept` 속성과 서버 검증 기준도 동일하게 맞췄다.

### 결과

클라이언트와 서버 모두 JPG, PNG, WEBP 파일만 허용하도록 검증 기준을 통일했다.

## 5. 기록 수정 시 이미지가 5장을 초과하는 문제

### 증상

기존 이미지가 있는 기록에서 신규 이미지만 검사하면 최종 이미지 수가 최대 5장을 초과할 수 있었다.

### 원인

기존 이미지, 삭제 예정 이미지, 신규 이미지 수를 함께 계산하지 않았다.

### 해결

서버에서 최종 이미지 수를 다음과 같이 계산했다.

```text
최종 이미지 수 = 기존 이미지 수 - 삭제 예정 이미지 수 + 신규 이미지 수
```

결과가 5장을 초과하면 저장을 중단했다. 프론트엔드에도 같은 계산을 적용해 파일 선택 시점에 즉시 안내했다.

### 결과

프론트엔드와 서버에서 모두 최대 5장 제한을 검증하여 요청값을 직접 조작해도 제한을 우회할 수 없게 되었다.

## 6. 다른 성장 기록의 미디어를 삭제할 수 있는 문제

### 원인

미디어 번호의 존재 여부만 확인하면 요청값을 조작해 다른 성장 기록에 속한 미디어를 삭제할 가능성이 있었다.

### 해결

삭제 요청된 모든 미디어가 현재 수정 중인 성장 기록에 속하는지 서버에서 다시 검사했다. 존재하지 않거나 다른 기록에 속한 미디어가 하나라도 포함되면 전체 삭제 요청을 거부했다.

### 결과

수정 요청값을 조작하더라도 다른 사용 기록의 미디어를 삭제할 수 없도록 소유권 검증을 보완했다.

## 7. DB에서 미디어를 삭제해도 S3 파일이 남는 문제

### 원인

JPA의 Cascade와 `orphanRemoval`은 DB 엔티티만 삭제하며 외부 저장소의 S3 객체는 자동으로 삭제하지 않는다.

### 해결

- 이미지 미디어 삭제 전에 S3 객체 삭제
- 이후 DB의 `Media` 데이터 삭제
- 성장 기록 삭제 시에도 연결된 미디어 정리 로직을 먼저 호출

### 결과

DB 데이터와 S3 객체가 함께 정리되어 사용되지 않는 고아 파일이 남지 않도록 개선했다.

## 8. YouTube 썸네일 URL 생성 오류

### 증상

생성된 YouTube 썸네일 이미지가 정상적으로 표시되지 않았다.

### 원인

`vi`와 영상 ID 사이의 `/`가 누락되었다.

```text
https://img.youtube.com/viVIDEO_ID/hqdefault.jpg
```

### 해결

```java
return "https://img.youtube.com/vi/"
        + youtubeVideoId
        + "/hqdefault.jpg";
```

### 결과

정상적인 YouTube 썸네일 주소가 생성되도록 수정했다.

## 9. `updatedAt` 값이 수정 시 갱신되지 않는 문제

### 원인

`@UpdateTimestamp` 필드에 `updatable = false`가 함께 지정되어 UPDATE SQL에 해당 컬럼이 포함되지 않았다. 카테고리의 수정일에는 `@CreationTimestamp`가 잘못 사용되고 있었다.

### 해결

```java
@UpdateTimestamp
@Column(name = "updated_at", nullable = false)
private LocalDateTime updatedAt;
```

### 결과

엔티티가 수정될 때 수정 일시도 함께 갱신될 수 있도록 매핑을 바로잡았다.

## 10. Builder 사용 시 미디어 목록이 `null`이 되는 문제

### 원인

Lombok `@Builder`는 필드 선언부의 초기값을 자동으로 빌더 기본값으로 사용하지 않는다.

### 해결

```java
@Builder.Default
private List<Media> mediaList = new ArrayList<>();
```

### 결과

빌더로 생성한 성장 기록에서도 미디어 컬렉션이 빈 리스트로 안전하게 초기화되도록 했다.

## 11. 테스트가 운영 DB와 외부 설정에 의존하는 문제

### 원인

Spring Context 테스트가 기본 설정을 그대로 사용해 MySQL, AWS, 메일 설정이 없는 로컬 또는 CI 환경에서 실패할 수 있었다.

### 해결

- 테스트 클래스에 `@ActiveProfiles("test")` 적용
- H2 인메모리 DB와 MySQL 호환 모드 사용
- 테스트용 AWS Region, S3 버킷, 메일 설정 분리

### 결과

운영 MySQL에 연결하지 않고 독립적인 환경에서 Spring Context 테스트를 실행할 기반을 마련했다.

## 12. 이메일 발송 오류의 내부 정보가 노출되는 문제

### 원인

이메일 발송 실패 시 `e.getMessage()`를 사용자 응답에 그대로 포함하고 있었다.

### 해결

상세 예외는 SLF4J 로그에 기록하고 사용자에게는 일반화된 메시지를 반환했다.

```java
log.error(
    "이메일 인증번호 발송에 실패했습니다. email={}",
    email,
    e
);
```

```text
이메일 발송에 실패했습니다. 잠시 후 다시 시도해 주세요.
```

### 결과

개발자는 서버 로그에서 상세 원인을 확인하면서 사용자에게 내부 시스템 정보가 노출되는 것을 방지했다.

5. 브라우저에서 타임라인 화면 재검증

- 주요 모바일 해상도와 실기기 UI 검수

## 회고

오늘 발생한 문제는 주로 브라우저와 서버 사이의 데이터 바인딩, DB와 외부 저장소 사이의 데이터 일관성, 실행 환경에 따른 외부 설정 차이에서 발생했다.

화면에서만 입력을 제한하지 않고 서버에서도 동일한 검증을 수행하도록 보완했다. 또한 외부 서비스 오류를 원인별로 구분하여 이후 장애 발생 시 더 빠르게 진단할 수 있도록 개선했다.
