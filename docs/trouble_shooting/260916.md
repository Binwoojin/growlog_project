## 1. Day 11 검증 스크립트가 스크린샷 저장 후 TypeError를 던지는 문제

### 문제 상황

Day 11 UI 상태(Loading/Empty/Error/Success 등 18개 화면)를 캡처하는
Playwright 스크립트를 실행한 직후, 콘솔에 다음과 같은 예외가
출력되었다.

```text
TypeError: Cannot read properties of undefined (reading 'fulfill')
    at RouteHandler._handleInternal (.../network.js:693:23)
```

### 원인

스크립트가 각 화면을 순회하며 `context.close()`로 브라우저 컨텍스트를
닫은 뒤에도, 그 컨텍스트에 등록해 둔 라우트 핸들러 중 하나가 뒤늦게
비동기로 실행되면서 이미 사라진 `route` 객체의 `fulfill()`을 호출하려
했다. 즉 검증 스크립트 자체의 teardown 순서 문제였다.

### 확인

예외가 발생하기 전에 콘솔에는 이미 "DONE"이 출력되어 있었고, 목표로
했던 18개 스크린샷 파일이 `docs/screenshots/day11/`에 모두 정상적으로
생성되어 있음을 `ls`로 확인했다. 즉 실제 화면 렌더링이나 앱 코드와는
무관한, 검증 스크립트 정리 단계의 문제였다.

### 처리

애플리케이션 코드를 수정할 이유가 없다고 판단해 별도 수정 없이
넘어갔다. 스크린샷 자체는 육안으로 확인해 Day 11에서 추가한 폼 검증
UI(빈 제목/200자 초과/기간 역전 에러 문구)와 삭제 확인 플로우가
모두 올바르게 렌더링된 것을 확인했다.

### 배운 점

- Playwright에서 `context.close()` 이후에도 그 컨텍스트에 등록한
  라우트 핸들러의 콜백이 비동기로 실행 중이었다면 예외가 발생할 수
  있다 — 검증 스크립트 자체의 안정성 문제와 검증 대상 애플리케이션의
  문제를 구분해서 판단해야 한다.
- 스크립트가 예외로 끝나도 그 전에 의도한 산출물(스크린샷 파일)이
  전부 생성되었는지를 먼저 확인하면, 불필요하게 원인을 앱 코드에서
  찾느라 시간을 쓰지 않을 수 있다.

## 2. Record Detail 화면의 YouTube 임베드가 검증 환경에서 비어 보이는 문제

### 문제 상황

Day 13에서 구현한 Record Detail 화면(`RecordDetailView.vue`)의 성공
상태를 Playwright로 캡처했을 때, 첨부 이미지는 정상적으로 보였지만
YouTube `<iframe>` 영역이 완전히 비어 있었다.

### 원인 확인

`.record-detail__youtube`/`.record-detail__image` 두 요소의
`boundingBox()`를 각각 출력해서 실제로 레이아웃 공간이 잡혔는지부터
확인했다.

```text
media box: { x: 55, y: 271.5, width: 590, height: 935.875 }
img box:   { x: 55, y: 271.5, width: 592, height: 592 }
yt box:    { x: 55, y: 875.5, width: 590, height: 331.875 }
```

`aspect-ratio: 16 / 9`로 지정한 높이(331.875 ≈ 590 × 9/16)가 정확히
계산되어 있어 CSS 자체는 문제가 없었다. `page.on('requestfailed', ...)`로
실패한 요청을 확인하자 원인이 드러났다.

```text
FAILED: https://www.youtube.com/embed/dQw4w9WgXcQ  net::ERR_TUNNEL_CONNECTION_FAILED
```

이 세션이 실행되는 샌드박스 환경은 아웃바운드 네트워크가 사전 설정된
프록시를 통해서만 나가도록 제한되어 있고, `youtube.com`은 그 허용
목록에 없어서 발생한 `ERR_TUNNEL_CONNECTION_FAILED`다 — 앱 코드나
백엔드가 내려주는 URL(`https://www.youtube.com/embed/{videoId}`)의
문제가 아니라, 검증에 사용한 샌드박스 환경 자체의 네트워크 제약이었다.

### 확인 방법

첨부 이미지도 같은 문제인지 구분하기 위해, 외부 이미지 호스팅
URL(`https://placehold.co/...`, 오타까지 포함해 실제로는 잘못된
URL이었다) 대신 `data:image/png;base64,...` 형태의 인라인 이미지로
바꿔 다시 캡처했더니 정상적으로 렌더링되는 것을 확인했다 — 이미지
쪽은 외부 네트워크에 의존하지 않는 실제 배포 환경(S3 Presigned URL)과
동일한 종류의 URL이므로 실제 배포에서는 문제가 없을 것으로 판단했다.

### 처리

애플리케이션 코드는 수정하지 않았다. 실제 배포 환경에서는 사용자의
브라우저가 일반적인 인터넷 접근 권한을 가지므로 다른 웹사이트의
YouTube 임베드와 동일하게 정상 로드된다 — 이번 세션의 검증 전용
네트워크 제약일 뿐이다. 다만 Day 14(배포/운영 QA)에서 실제 배포
환경이 확보되면 이 부분(이미지 Presigned URL, YouTube 임베드)을
다시 한번 실환경에서 확인해야 한다는 점을 후속 작업으로 남긴다.

### 배운 점

- 스크린샷이 비어 보인다고 바로 앱 버그로 단정하지 말고, 레이아웃
  치수(`boundingBox`)와 실패한 네트워크 요청을 먼저 분리해서 확인하면
  "코드 문제"와 "검증 환경 제약"을 빠르게 구분할 수 있다.
- 외부 도메인에 의존하는 기능(YouTube 임베드 등)을 샌드박스/CI처럼
  네트워크가 제한된 환경에서 검증할 때는, 레이아웃/치수까지만
  확인하고 실제 콘텐츠 로드는 별도로(실제 배포 환경 또는 네트워크
  제한이 없는 환경에서) 확인해야 한다는 점을 Day 14 QA 체크리스트에
  반영해야 한다.
